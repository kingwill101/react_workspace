# Testing

Use `react_testing` and `server_testing` as the default test stack. Each
harness isolates one layer, so most behavior can be verified without external
browser automation.

## Install

```yaml
dev_dependencies:
  react_testing:
    git:
      url: https://github.com/kingwill101/react_workspace.git
      ref: master
      path: packages/react_testing
  server_testing: ^0.4.0
  test: ^1.31.2
```

Add the adapter that matches the application server:

- Shelf: the hosted `server_testing_shelf` package;
- Routed: `routed_testing` from the same `routed` Git ref as `routed_core`.

These packages are currently consumed from Git refs because they are not yet
published to pub.dev. Replace `master` with an immutable commit for
reproducible external applications.

## Component and hook tests

`ReactComponentHarness` installs an in-memory React binding and renderer:

```dart
test('renders a portable host tree', () {
  final harness = ReactComponentHarness();
  final node = harness.run(
    () => div(id: 'message', children: ['Hello']),
  ) as HostNode;

  harness.assertHostNode(node, namespace: 'web', name: 'div');
  harness.assertText(node.children.single, 'Hello');
});
```

Use it for node trees, hook state, contexts, refs, events, and runtime
capability checks.

## Server functions

`ServerFunctionHarness` supports direct typed dispatch:

```dart
final harness = ServerFunctionHarness();
harness.registry.register(greetRef, (args, context) => 'Hello ${args.name}');

final result = await harness.dispatch(greetRef, (name: 'Ada'));
expect(result, 'Hello Ada');
```

For HTTP envelopes, authentication, body limits, content types, and contract
mismatches, compose the registry into the real server application. Adapt that
application with `ShelfRequestHandler`, `RoutedRequestHandler`, or the
matching server-testing adapter and create a test client from the harness.

## SSR

Use `InMemorySsrHarness` for template/props substitution and
`SsrTestHarness` for the worker protocol and failure handling.

```dart
final harness = SsrTestHarness();
harness.mockRender('<main>SSR</main>', props: {'title': 'Test'});
final ssr = await harness.start();

final rendered = await ssr.render(component: 'test.Root', props: {});
expect(rendered.html, '<main>SSR</main>');

await harness.close();
```

## Built full stack

`ReactTestHarness` runs the actual `react build` pipeline and starts the
generated Node worker on a harness-allocated port. Compose its `ssrClient`,
`indexTemplate`, and `outputDirectory` into the real application, then use
the application's server-testing adapter.

```dart
final react = await ReactTestHarness.start(
  projectRoot: Directory.current,
);

final app = createApplication(
  ssr: react.ssrClient,
  indexTemplate: react.indexTemplate,
  staticRoot: react.outputDirectory,
);
final client = react.createClient(RoutedRequestHandler(app.handler));

final response = await client.get('/deep/link');
response.assertStatus(200).assertBodyContains('SSR');

await client.close();
await react.close();
```

Use `GeneratorFidelityHarness` for generated Web API completeness and host
type coverage.

## Verification order

For maintained examples:

1. `dart analyze --fatal-infos`;
2. `dart test`;
3. `ReactTestHarness` plus the actual server adapter;
4. `dart run react_tool:react build` when production artifacts are explicitly
   in scope.

Browser automation is reserved for behavior the native harnesses cannot
represent. When such a gap appears, prefer extending `react_testing` first.
