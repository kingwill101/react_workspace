# Code generation

`react_codegen` turns annotated Dart functions into portable component
factories, JavaScript bridges, SSR registries, and server-function contracts.
Applications consume a small public generated surface while implementation
details stay under `lib/.generated/`.

## Component source

A component is an authored function with one named record parameter:

```dart
import 'package:react_dom/react_dom.dart';

@reactComponent
ReactNode Avatar(({
  required String src,
  String? label,
  ReactChildren children,
}) props) {
  return figure(
    children: [
      img(src: props.src, alt: props.label ?? ''),
      ...props.children,
    ],
  );
}
```

The shared analyzer validates the return type, record shape, children type,
callback bridgeability, and generated component identity before emission.

## Generated component files

For `lib/avatar.dart`, the cache builders produce:

- `avatar.react.dart`: portable component ID, callable factory, and props
  builder;
- `avatar.react.g.dart`: browser registration and Dart/JavaScript prop codecs.

Aggregate builders also produce:

- `react_components.g.dart`: browser component registration;
- `ssr_registry.g.dart`: server-rendering component identities;
- `server_actions.g.dart`: server-function dispatch.

`react_tool` copies these cache outputs into `lib/.generated/` and rewrites
relative imports for that location. Entrypoints import the generated public
surface with package URIs:

```dart
import 'package:my_app/.generated/avatar.react.dart';
import 'package:my_app/.generated/react_components.g.dart';
```

Authored component files do not import their own generated factories. Browser
and SSR entrypoints import factories and registries when assembling the app.

## Factory and builder ergonomics

The generated factory supports direct named arguments:

```dart
Avatar(
  key: 'profile-avatar',
  src: user.avatarUrl,
  label: user.name,
)
```

It also exposes a mutable props builder for composition-heavy code:

```dart
final avatar = Avatar.props()
  ..key = 'profile-avatar'
  ..src = user.avatarUrl
  ..label = user.name;

return avatar();
```

Required values are `late` fields, so callers must initialize them before
calling the builder. Children are normalized to portable `ReactNode` values
for both browser rendering and SSR.

## Server functions

`@serverFunction` generation produces a stable function ID, typed argument and
result codecs, a browser client proxy, and server dispatch registration.
`@serverData` types receive nested codecs used by both ends of the contract.

Generated server-function outputs remain transport-neutral. Shelf and Routed
HTTP integration lives in `react_server_shelf` and `react_server_routed`
respectively.

## Running generation

Use the React CLI for normal application development:

```console
dart run react_tool:react generate
```

`react build` and `react serve` invoke the same generation phase before
compilation. Running `build_runner` directly is useful only while debugging a
builder because its outputs stay in the build cache and are not synchronized
into `lib/.generated/`.

Generated output is disposable:

- never hand-edit it;
- ignore `lib/.generated/` in source control;
- fix the reader, model, emitter, or scaffold template;
- regenerate and run analysis/tests;
- run generation twice when checking determinism.

## Generator architecture

The generators separate responsibilities deliberately:

1. readers convert analyzer elements or TypeScript declarations into typed IR;
2. registries deduplicate and name referenced types;
3. emitters render one output concern;
4. `react_tool` formats and synchronizes generated sources;
5. fidelity and structure tests protect completeness and maintainability.

A new feature should extend the model first and keep browser and SSR output
derived from the same contract. Avoid target-specific string patches after
emission.
